### ⚠️ The recurring CI failure (lockfile hygiene)
Three CI runs died in ~12s at "Install dependencies" (`fafdb27`, `4d45194`,
`58c575f`): each was a Google AI Studio export that **rewrote
`package-lock.json` from the sandbox's own node_modules**, dropping entries
like `recharts` that `package.json` requires. `npm ci` is deliberately strict
(EUSAGE: "package.json and package-lock.json not in sync") so the build never
even started — the page code was never the problem. Fixed by restoring the
lock from the last good commit (`git checkout 29d8793 -- package-lock.json`,
valid because `package.json` never changed). Workflow rule going forward:
AI Studio output enters this repo **as source files only**, through a branch/
PR — never with its `package-lock.json`, and never straight to `main`.

### Why #15 is not free
`getResponsiveImageProps()` returns props spread onto plain `<img>` tags in
**9 places** (verified at `ef6db57`: `App.tsx` ×8 — lines 2753, 3146, 3478,
5353, 5552, 6033, 6669, 6770 — and `UmrahLandingPage.tsx` ×1). AVIF needs
`<picture><source type="image/avif">…</picture>`, i.e. a shared component or 9
call-site edits, **plus** the preload path in `index.html` and
`scripts/prerender.ts`. Worth ~29–55% more image bytes on the LCP hero (measured,
see Appendix A.2); do it as its own change with its own verify-build guards.
**Full file-level plan: Appendix A.**

#### 2A. Re-compress WebP Images — ⏸ SUPERSEDED
**Problem:** 183KB unnecessary image weight

**Decision:** do not re-encode WebP→WebP. Generate all breakpoints from
`src/assets/optimized-social/*.jpg` (the committed masters) with
`scripts/optimize-images-production.sh`, whose `SOURCE_DIR` now defaults to
that directory. On 2026-10-04 the 42 missing 960w variants were generated this
way (quality 78, effort 6; ~35% smaller than their 1200w twins; hero 69KB →
46KB). Sizes measured after generation:

```

largest: maldives_destination 132KB (vs 209KB at 1200w)
hero LCP: clouds_boat_hero 46KB (vs 69KB at 1200w)
```

The script body below is kept for reference only — prefer
`optimize-images-production.sh`:

**Target Files:**
```
public/assets/images/bangkok_destination_1781544149435-1200.webp (142KB → 56KB)
public/assets/images/nepal_destination_1781544132297-1200.webp (131KB → 56KB)
public/assets/images/clouds_boat_hero_1781438671378-1200.webp (69KB → 48KB)
public/assets/images/maldives_destination_1790387286896-640.webp (70KB → 30KB)
public/assets/images/dubai_destination_1781544180311-640.webp (49KB → 16KB)
public/assets/images/singapore_destination_1790387270177-640.webp (50KB → 30KB)
```

**Compression Script:**
```bash
#!/bin/bash
# scripts/optimize-images.sh

IMAGE_DIR="public/assets/images"
QUALITY=78
METHOD=6

for file in "$IMAGE_DIR"/*-1200.webp; do
  echo "Optimizing: $file"
  cwebp -q $QUALITY -m $METHOD -af "$file" -o "$file.tmp"
  mv "$file.tmp" "$file"
done

for file in "$IMAGE_DIR"/*-640.webp; do
  echo "Optimizing: $file"
  cwebp -q 76 -m 6 -af "$file" -o "$file.tmp"
  mv "$file.tmp" "$file"
done
```

**Quality Settings:**
- Hero images: Quality 80 (preserve detail)
- Destination cards: Quality 78
- Thumbnail images: Quality 76

**Expected Impact:** -183KB transferred, -0.8s LCP on 3G

**Problem:** 140.8KB unused GTM JavaScript on initial load

```html
<!-- BEFORE: Synchronous GTM -->
<script async src="https://www.googletagmanager.com/gtag/js?id=G-2EWKHC1KE1"></script>
<script>
  window.dataLayer = window.dataLayer || [];
  function gtag(){dataLayer.push(arguments);}
  gtag('js', new Date());
  gtag('config', 'G-2EWKHC1KE1');
</script>

<!-- AFTER: Interaction-deferred GTM -->
<script>
  (function() {
    let gtmLoaded = false;
    const loadGTM = () => {
      if (gtmLoaded) return;
      gtmLoaded = true;
      
      // Load gtag.js
      const script = document.createElement('script');
      script.async = true;
      script.src = 'https://www.googletagmanager.com/gtag/js?id=G-2EWKHC1KE1';
      document.head.appendChild(script);
      
      // Initialize dataLayer
      window.dataLayer = window.dataLayer || [];
      function gtag(){dataLayer.push(arguments);}
      window.gtag = gtag;
      gtag('js', new Date());
      gtag('config', 'G-2EWKHC1KE1');
    };
    
    // Load on interaction OR after 5 seconds
    ['scroll', 'click', 'mousemove', 'touchstart'].forEach(event => {
      window.addEventListener(event, loadGTM, {once: true, passive: true});
    });
    setTimeout(loadGTM, 5000);
  })();
</script>
```

#### 3B. Lazy-Load Emerald Script
**Problem:** 64.6KB affiliate script (34.3KB unused) loads eagerly

```html
<!-- BEFORE: Immediate load -->
<script nowprocket data-noptimize="1" data-cfasync="false">
  (function () {
    var script = document.createElement("script");
    script.async = true;
    script.src = "https://emrld.ltd/NTQwMjc3.js?t=540277";

    document.head.appendChild(script);

<script nowprocket data-noptimize="1" data-cfasync="false">
  (function () {
    if ('IntersectionObserver' in window) {
      const observer = new IntersectionObserver((entries) => {
        if (entries[0].isIntersecting) {
          const script = document.createElement("script");
          script.async = true;
          script.src = "https://emrld.ltd/NTQwMjc3.js?t=540277";
          script.onerror = function () {};
          document.head.appendChild(script);
          observer.disconnect();
        }

      // Observe footer or main content end
      const target = document.querySelector('footer') || document.querySelector('#root');
      if (target) observer.observe(target);
    } else {
      // Fallback: load after 10 seconds
      setTimeout(() => {
        const script = document.createElement("script");
        script.async = true;
        script.src = "https://emrld.ltd/NTQwMjc3.js?t=540277";
```

## 🔐 Consent Mode v2 (GDPR) — ✅ IMPLEMENTED 2026-10-04

Not a CWV item, but it gates serving EU traffic, so it tracks here too. Full
playbook: `GTM_CONSENT_MODE_INTEGRATION.md`. What shipped:

1. **Inline default-state script in `index.html`**, before the deferred GTM
   loader: every storage type resolves to `denied` unless a stored choice says
   otherwise, `security_storage` granted, `wait_for_update: 500`. Storage keys:
   `cookie-consent` (accepted/declined/custom) + `cookie-consent-settings`
   (per-category JSON).
2. **`src/components/ConsentBanner.tsx`** — bilingual (EN/BN) granular CMP:
   Accept all / Decline / per-category customize panel (necessary, analytics,
   marketing, functionality), `role="dialog"`, links to `/privacy`
   (`/bn/privacy`). Updates go through `updateGoogleConsentMode()`, which
   shims `window.gtag` onto `dataLayer` if GTM has not booted yet (it is
   deferred), and emits a `consent_update` dataLayer event +
   `ural:consent-updated` CustomEvent.
3. **Withdrawal path (GDPR Art. 7(3))**: footer "Cookie settings" button and
   the Privacy Policy "Change Preferences" button both dispatch
   `ural:open-cookie-banner`, which reopens the banner with the customize
   panel.
4. **Mounted** in `App.tsx` as `<ConsentBanner onNavigate={navigateTo} lang={lang} />`.
5. **CI guard**: `verify-build.ts` fails if the consent default ever ships
   after the GTM loader, or if `analytics_storage` can no longer default to
   denied (whitespace-tolerant so reformatting the head script won't trip it).

# 📎 Appendix A — Phase 6A AVIF rollout plan (`<picture>`)

**Status:** ⏳ **plan only — nothing in this appendix is implemented.**  
**Written:** 2026-10-04, against `ef6db57` (`main` tip at the time). Re-verify the
line numbers before executing; they are exact as of that commit.

This appendix exists because §6A is a one-line stub. Everything below is tied to
actual files in this repo, including the three traps that make the "swap WebP
for AVIF" one-liner wrong here: a non-global prerender regex, an exact-equality
preload guard, and the fact that a `<picture>` + a mismatch between preload
format and render format silently downloads the LCP image **twice**.

## A.1 How the image path works today (verified at `ef6db57`)

| Piece | File | Behavior |
|---|---|---|
| Breakpoint list | `src/utils/imageAssets.ts:56` | `RESPONSIVE_IMAGE_BREAKPOINTS = [640, 960, 1200]` |
| srcset builder | `src/utils/imageAssets.ts:70` | `buildResponsiveSrcSet(src1200)` — **hardcodes `-${w}.webp`** |
| React call sites | `src/App.tsx` ×8 (2753, 3146, 3478, 5353, 5552, 6033, 6669, 6770), `src/components/UmrahLandingPage.tsx:92` | `{...getResponsiveImageProps(src, sizes)}` spread onto a plain `<img>`; every `<img>` carries `width`/`height` (CLS), `loading`, `fetchPriority`, `decoding`, `className` |
| SPA shell preload | `index.html:24` | hand-written `<link rel="preload" as="image" type="image/webp" … imagesrcset=…>` for the homepage hero |
| Route preloads | `scripts/prerender.ts:2344` | builds the per-route LCP preload from `buildResponsiveSrcSet()`; the shell's tag is stripped by the regex at `:2369` |
| Prerendered HTML | — | **contains no photo `<img>`** — the hero markup is client-rendered after hydration, so the preload link is the only early image hint the browser gets |
| Cache headers | `public/_headers` | `/assets/*` → `max-age=31536000, immutable`; a `.avif` under `/assets/images/` inherits this — **no header change needed** |
| Assets today | `public/assets/images` / `src/assets/optimized-social` | 126 WebP (11 MB) generated from 42 JPG masters (7.1 MB) |

Consequence of the "no `<img>` in HTML" row: **the preload decides the LCP
fetch.** A `<picture>` element only exists after hydration, so upgrading the
markup without upgrading the preload leaves the early fetch on WebP and the
AVIF only helps below-the-fold images. A.5 is not optional polish; it is where
the LCP win is.

## A.3 Step 1 — generate the 126 AVIF files (inert commit)

Same rule as Phase 2A, for the same reason: **encode from
`src/assets/optimized-social/*.jpg`, never from the WebPs** (generational loss).
Output naming mirrors WebP: `<stem>-<w>.avif` beside `<stem>-<w>.webp`, widths
640/960/1200 → 42 × 3 = 126 new files.

Encoder options, in order of preference:

1. **`avifenc` (libavif/AOM)** — no npm dependency, so no lockfile churn:
   ```bash
   avifenc -s 6 -q 50 -w 640  master.jpg out-640.avif    # slow but small
   avifenc -s 6 -q 50 -w 960  master.jpg out-960.avif
   avifenc -s 6 -q 55 -w 1200 master.jpg out-1200.avif
   ```
   `-s` is encoder speed 0–10; on 42 masters anything ≤ 6 is tolerable offline.
2. **`sharp` (npm devDependency)** — most portable if the CLI is unavailable on
   the owner's Windows machine, but it adds a native dependency and rewrites
   `package-lock.json`: that lockfile must be generated by **local npm**, never
   by an external sandbox export (see the lockfile-hygiene section at the top).
3. **ImageMagick 6.9.11 + libheif** — what produced A.2:
   ```bash
   convert master.jpg -resize 960x -quality 55 out-960.avif
   ```
   Requires a build with HEIC/AVIF delegates (`convert -list format | grep AVIF`
   shows `rw+`); not guaranteed on other machines.

Add the same three-tier block to `scripts/optimize-images-production.sh`
(behind a `command -v avifenc` preflight mirroring the existing `cwebp` check).
Budget check: 126 extra files, each well under 1 MB — Cloudflare Pages allows
20,000 files/site and 25 MiB per file on Free, so this is a non-issue. Total
`public/assets/images` grows ~11 MB → ~17–19 MB, of which a given visitor still
fetches only the handful of files their page actually needs.

Commit this **alone**. Nothing references the AVIFs yet, so it cannot regress
anything and can be reverted independently.

## A.4 Step 2a — the `ResponsiveImage` component (9 call sites)

`buildResponsiveSrcSet` gains an extension parameter, defaulted to `webp` so
every existing caller and guard keeps working while the migration is in flight:

```ts
export function buildResponsiveSrcSet(
  src1200: string,
  ext: "webp" | "avif" = "webp",
): string {
  return RESPONSIVE_IMAGE_BREAKPOINTS.map(
    (w) => `${src1200.replace(/-1200\.webp$/, `-${w}.${ext}`)} ${w}w`,
  ).join(", ");
}
```

The component keeps `getResponsiveImageProps()`'s job — intrinsic `width`/`height`
for CLS, one `sizes` value for both sources — and puts every existing attribute
back on the `<img>`:

```tsx
// src/components/ResponsiveImage.tsx
export function ResponsiveImage({
  src, sizes = "100vw", alt, ...imgProps
}: { src: string; sizes?: string; alt: string } &
   ImgHTMLAttributes<HTMLImageElement>) {
  // small refactor: extract the dimension lookup that lives inside
  // getResponsiveImageProps() today so both paths share it
  const { width, height } = getResponsiveImageDimensions(src);

  return (
    <picture className="contents">
      <source type="image/avif" srcSet={buildResponsiveSrcSet(src, "avif")} sizes={sizes} />
      <source type="image/webp" srcSet={buildResponsiveSrcSet(src, "webp")} sizes={sizes} />
      <img src={src} alt={alt} width={width} height={height} {...imgProps} />
    </picture>
  );
}
```

**Trap 1 — layout.** All 9 `<img>` elements are positioned by their classes
(`absolute inset-0 h-full w-full object-cover`) inside a positioned or
aspect-ratio parent. `<picture>` is `display: inline` by default, so a naive
wrapper breaks percentage heights and absolutely-positioned children. The
`className="contents"` (`display: contents`) on `<picture>` keeps the `<img>` a
direct layout child of the existing parent, so the 9 markup changes are
attribute-for-attribute mechanical: `{...getResponsiveImageProps(x, sizes)}`
becomes `<ResponsiveImage src={x} sizes={sizes} … />` with the rest of the JSX
untouched. Still verify visually at all 9 sites: homepage hero, destination
tiles, both blog grids, blog article figure, Umrah hero, and the mid-page
newsletter band.

**Trap 2 — `alt` and `aria-hidden`.** They stay on the `<img>`, never on
`<picture>`/`<source>`; decorative images keep `alt="" aria-hidden`.

After migration, keep a source-level guard so a future call site cannot bypass
the component (see A.6) — otherwise the next feature silently ships WebP-only
again.

## A.5 Step 2b — the preload, in the *same commit* (this is the trap)

Because the prerendered HTML has no `<img>` (A.1), the browser's early fetch is
driven entirely by `<link rel="preload" as="image">`. Two rules:

**Rule 1 — preload exactly one format, the AVIF, with `type="image/avif"`:**

```html
<link rel="preload" as="image" type="image/avif"
      href="/assets/images/clouds_boat_hero_1781438671378-1200.avif"
      imagesrcset="…-640.avif 640w, …-960.avif 960w, …-1200.avif 1200w"
      imagesizes="100vw" fetchpriority="high" />
```

**Rule 2 — do NOT add a WebP preload alongside it.** The `type` attribute only
makes a browser skip formats it *cannot decode*. Chrome 85+, Firefox 93+ and
Safari 16.4+ can decode both AVIF and WebP, so they honor **both** preloads and
download the hero twice — the exact regression this appendix exists to prevent.
Browsers without AVIF support simply skip the AVIF preload and pick the WebP
`<source>` when the picture renders (i.e. at hydration, a little later than the
old preload gave them). That population is Safari < 16.4 / Firefox < 93 — check
the share in Cloudflare analytics before deciding how much that matters; there is
no declarative way to preload WebP only for them.

**Rule 3 — the three copies of the preload must change together.** This is the
same three-way agreement whose absence caused the Google-Fonts incident noted in
`imageAssets.ts`:

| Copy | Location | Change |
|---|---|---|
| SPA shell | `index.html:24` | point `href`/`imagesrcset` at `.avif`, `type="image/avif"` |
| Route preloads | `scripts/prerender.ts:2344` | `buildResponsiveSrcSet(r.lcpImageUrl, "avif")` + `type="image/avif"` |
| Strip regex | `scripts/prerender.ts:2369` | **keep it matching exactly one tag** — it is `.replace(/\s*<link rel="preload" as="image"[^>]*\/>\n?/, …)` with **no `/g`**. Once the shell has a single AVIF preload the existing regex still works; if anyone emits two image-preload lines, this regex will strip only the first and every one of the ~163 prerendered routes will silently ship the homepage hero preload. If a second tag ever becomes necessary, convert the block to the two-tag pattern used for fonts (which *does* match both tags). |

Note on `imagesrcset`/`imagesizes` support: browsers that ignore the attribute
fall back to fetching `href` — today that is the 1200w WebP, after this change
the 1200w AVIF. Unchanged behavior class, but it is worth one line in the
network-panel check (A.6) that each page performs exactly **one** image request
per image.

**Why 2a and 2b are one commit:** an intermediate state where the preload format
and the render-selected format disagree makes some browser download both files
(preload warms A, `<picture>` picks B). Every split — component-first or
preload-first — creates that state on production for one deploy window. Land
them atomically.

## A.7 Risks, non-goals, and the decision to take first

- **Risk — quality acceptance.** Encoding artifacts are image-specific; the
  homepage hero is gradient-covered and undemanding, blog covers are not. Pick
  per-tier qualities (start 640: q50, 960: q50, 1200: q55), then compare crops
  of a hero and a text-heavy blog cover at 100%.
- **Risk — decode cost.** AV1 decode is heavier on low-end Android; it can shift
  LCP *after* the bytes arrive. Watch CrUX/field LCP on low-end devices, not
  just Lighthouse on a fast machine.
- **Risk — non-AVIF browsers** (Safari < 16.4, Firefox < 93) get their LCP image
  at hydration time once the WebP preload is dropped (A.5, Rule 2). Measure the
  share in Cloudflare analytics before committing to this; the cheap mitigation
  for the affected slice is keeping their old behavior by *not* shipping at all,
  which is why 6A is still labelled optional in the Status Board.
- **Non-goal — `/img/*` social/OG cards stay JPG/PNG.** Crawlers and social
  scrapers consume them; no LCP benefit; do not touch them here.
- **Non-goal — no Worker/edge negotiation.** Cloudflare Pages static assets do
  no `Accept`-header content negotiation. Cloudflare **Polish** (paid image
  optimization add-on) does exactly that at the edge and could deliver most of
  this with zero front-end change — worth a pricing check before the refactor if
  the plan ever includes it.
- **Standing rule still applies:** if `sharp` enters `package.json`, the
  lockfile is generated by local `npm install`, never by an external sandbox
  export (see "The recurring CI failure" at the top of this guide).
