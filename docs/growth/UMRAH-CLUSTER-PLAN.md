## 3. Accuracy gates before promotion

The 14 October claims ledger verifies the updated main guide only; it does **not** certify every existing child article or the interactive `/umrah` tool. Audit before adding a page to a prominent hub card, refreshing its excerpt, or making it a recommended next step.

1. **Audit the `/umrah` calculator and sales claims first.** The original audit target was a preset-price calculator and an unsupported agency-savings comparison; no matched, dated booking basket or comparable agency quote was recorded in the Umrah ledger. **18 October 2026 repository resolution:** the hub now uses `UmrahBudgetCalculator`, a shared EN/BN user-quote worksheet with no preset prices, assumed FX or savings arithmetic. Blank categories keep the result incomplete, and included/not-applicable items need explicit zero. Both prerendered pages contain the same component. This resolves the preset-input mechanism, not a live-price verification or the remaining child-article audit. The U-12 range stays a dated, unre-priced reference only. See [`HAJJ-UMRAH-CLOSURE.md`](HAJJ-UMRAH-CLOSURE.md) for tests and remaining release/source gates.
2. **Keep the article's preserved estimate in its approved scope.** It was not repriced in the research task. Keep its unre-priced planning qualifier and do not use the estimate to infer agency savings or current component prices.
3. **Run a claims-ledger review for each child independently.** In particular, check the existing stopover page's fixed-price/hotel statements; the Nusuk page's universal biometric and slot-timing language; hotel distance/shuttle and elderly-accessibility claims; women's access/eligibility claims; Ramadan savings; religious Ihram/Miqat statements; and Zamzam/customs allowances. These are audit targets, not findings that every claim is false.
4. **Do not use the on-site topical matrix as demand evidence.** `TopicalAuthorityBlueprint.tsx` contains `monthlyIntentSignal`, keyword lists, and answer-copy hypotheses. They are not a GSC export, live SERP study, or source ledger. Reuse only after each claim and demand label has been independently verified; otherwise mark it “not measured” or remove it from public-facing promotion.
5. **Re-check seasonal and dynamic sources at release time.** The Umrah calendar, health rules, visas, permits, Hajj restrictions, rail prices, airline terms, hotel availability, and exchange rates can change. The original 14 October 2026 ledger and subsequent scoped 19 October reviews in `CONTENT-QUEUE.md` / `DIY-UMRAH-SOURCE-REVIEW.md` are not a substitute for a fresh check before later-season advice. The main guide now has attributed foreign-document criteria and a pre-payment caution, but current carrier/GCC/digital-entry limits remain open; the stopover follow-up is recorded separately; hotel/rail is now separately recorded; flight strategy is now separately recorded; women-specific guidance is now separately recorded; the next independent asset is older travellers/elderly parents.

## 6. Measurement and definition of a released wave

For each page asset, record the approved English/Bengali paths, owner approval, deployment date, source-check date, live-route result, and any sitemap/RSS change. Verify the live pages' HTTP response, language, canonical/hreflang, title, body, visible FAQ/schema, official source links, and internal destinations. Confirm no draft route or unapproved cluster page was included.

Use Search Console when access is available: inspect page- and query-level impressions, clicks, CTR, and query mix for Bangladesh over a stated date range; note index status, seasonality, low data, and other changes. Use comparable windows when the Umrah season makes a simple month-to-month comparison misleading. If data is unavailable or insufficient, record “not measured”—do not claim that one content edit caused a ranking change or promise a ranking timeline. Review the cluster as a whole after its approved waves are live; do not make ranking movement a prerequisite for the next release.

A wave is ready to close only after the owner approves publication, the EN/BN routes pass live checks, planned links resolve, and the queue records the release and measurement checkpoint. No wider cluster is considered complete merely because one article's build passes.
